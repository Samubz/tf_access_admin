## 3. Notification Creation and Delivery

- [x] 3.1 Add `Visit::NotificationStatuses` concern (`pending`/`delivered`/`failed`/`no_recipients`) and migration adding `visits.notification_status` (string, default `"pending"`).
- [x] 3.2 Add `audited` to `Notification`, covering at least `status`, `last_error`, `sent_at`, `attempts_count`, so each delivery attempt (including resend attempts) is preserved in history rather than overwritten.
- [x] 3.3 Update `Visits::Create#call` to, after the transaction commits, synchronously resolve `UnitOccupancy.active_authorizers_for(visit.unit)` and create one `Notification` per resident (`notification_type: NotificationTypes::VISIT_REQUEST`, `channel: NotificationChannels::PUSH`, `status: "pending"`, `notifiable: visit`, `recipient_person`, `unit`, `residential_property`). If there are zero active authorizers, set `visit.notification_status = "no_recipients"` immediately (no `Notification` rows, nothing to enqueue). (`Notifications::CreateForVisit`, called via `.tap` after the transaction block in `Visits::Create#call`.)
- [x] 3.4 For each created `Notification`, enqueue one `DeliverPushNotificationJob.perform_later(notification_id)` (`perform_later`, matching this codebase's `ProcessPeopleImportJob` convention — not raw Sidekiq `perform_async`). One job per resident — a resident has at most one device token per `DeviceToken`'s `has_one` design, so no per-token fan-out is needed. This delivers to whichever organization-independent device token the resident's `User` has registered, per the confirmed multi-organization behavior.
- [x] 3.5 Add `DeliverPushNotificationJob` with `sidekiq_options retry: false`. It loads the `Notification` and its `recipient_person.user&.device_token`; if absent, marks the `Notification` `skipped` (see note below — NOT left `pending`). If present, calls `Fcm::Client#send_notification`, increments `attempts_count`, and sets `status`/`sent_at`/`last_error` from the returned `Result`.
  - **Design correction made during implementation**: the original design said a no-token `Notification` "remains pending." That would make the Decision 7 rollup's "wait until no sibling is pending" check never resolve whenever any authorizer lacks a device token. Added a 4th `NotificationStatuses` value, `skipped` (terminal, not pending, no error), used exactly for this case. Updated `design.md` Decision 6/7 and the `fcm-push-notifications` spec scenario accordingly.
- [x] 3.6 After processing (success, failure, or skipped) — which, per 3.5, always happens exactly once and never crashes the job — `DeliverPushNotificationJob` takes a `Visit.lock` on the associated visit and re-evaluates all sibling `Notification` rows for that visit: if any are still `pending`, do nothing yet; otherwise set `visit.notification_status` to `delivered` (if any `sent`), `failed` (if any `failed`), or `no_recipients` (if all `skipped`).
- [x] 3.7 Ensure all recipient/notification resolution and the delivery job happen within the correct `ActsAsTenant` tenant context. (`DeliverPushNotificationJob` wraps its body in `ActsAsTenant.with_tenant(notification.organization)`, since Sidekiq reuses threads across jobs and must not inherit a stale tenant from a prior job.)

- [x] 4.2 Add `resend_notification` member route/action to `admin/visits` (alongside existing `authorize_visit`/`cancel`), authorized via `VisitPolicy#resend_notification?` (admin-only, `notification_status == "failed"` required), rejecting the request otherwise.
- [x] 4.3 Add a "resend notification" action to the admin visit detail view (`admin/visits/show`), visible/enabled only when `notification_status == "failed"`.
